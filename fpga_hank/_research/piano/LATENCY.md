## 1. 测量方法（不是估算，是实测分布）

note-on 相对 `sample_tick` 的相位是任意的（0..511 clk），所以延迟不是一个数而是一个**分布**。
`sim/tb/tb_piano_engine_latency.v` 把 **512 个相位全扫一遍**，每个相位独立复位后测一次：

- 对齐到 `sample_tick` → 偏移 p 拍 → 发 note-on → 数到输出出现
- `L1` = 第一个**非零**输出样本（严格"有输出"）
- `L2` = 第一个 `|mix_out| ≥ 32`（≈ −60 dBFS，保守的"可闻"）
- 另外测"8 声部占满后第 9 个音（抢占）"这一最坏场景

## 2. 实测结果（`evidence/latency_report.txt` / `latency_transcript.txt`）

| 口径 | min | P50 | P95 | P99 | max |
|---|---|---|---|---|---|
| **L1 首个非零样本** | 516 clk = **10.32 µs** | 772 = **15.44 µs** | 1001 = **20.02 µs** | 1021 = **20.42 µs** | 1027 = **20.54 µs** |
| **L2 \|mix\|≥32（≈−60 dBFS）** | 516 clk = 10.32 µs | 772 = 15.44 µs | 1001 = 20.02 µs | 1021 = 20.42 µs | 1027 = 20.54 µs |
| **抖动（max−min）** | — | — | — | — | **511 clk = 10.22 µs** |
| 抢占场景（8 声部占满后第 9 个音） | — | — | — | — | 549 clk = 10.98 µs |

**⇒ `piano_engine` 贡献的延迟 ≈ 0.0103 ~ 0.0205 ms（最大 20.5 µs）**
**⇒ 相对拓展③的 5 ms 要求，余量约 244 倍。**（基础要求②的 10 ms 更不在话下。）

### 延迟构成（为什么是这两个数）
| 环节 | 拍数 | 说明 |
|---|---|---|
| `on_valid` 被引擎采样 | 1 clk | 脉冲同步进 `clk` 域 |
| 声部分配 | **0 clk（纯组合）** | 分配与 `on_valid` 同拍完成 |
| 装载 FSM | **14 clk** | 2 拍/泛音 × 6 泛音 + 1 拍广播 |
| 等到下一个 `sample_tick` | **0..511 clk** | ← **抖动的唯一来源**（事件异步、采样同步） |
| 输出流水 | 3 clk | ROM → 乘包络 → 6 路求和 → 引擎混音 |
| 首个样本可能恰好为 0 | +512 clk（最坏） | 6 个泛音相位都从 0 起 ⇒ `sin(0)=0`；若该拍琴槌噪声快照也是 0 就要再等一个采样周期 |
| **合计** | **516 ~ 1027 clk** | 与实测完全吻合 |

### 关于"确定性"
- 抖动 **严格等于一个采样周期（511 clk = 10.22 µs）**，**不是随机噪声**，而是"异步事件被同步采样"的**相位量化**：
  延迟 = f(note-on 相位)，同一个相位永远得到同一个值（可复现）。
- 若事件源本身与 `sample_tick` 同步（例如 `song_player` 按采样点调度），抖动可降为 **0**（固定值）。
- 若事件源异步（UART/MIDI/按键），相位在 [0,511] 上均匀 ⇒ 延迟在 [10.3, 20.5] µs 上均匀，
  上表的分位数就是它的分布。**上界是确定的（20.5 µs），没有长尾。**

## 3. ★ 你问的"ADSR 起音算不算延迟" —— 分开回答

### 3.1 `piano_engine` 自己的包络：**起音 = 0 ms，不存在"起音延迟"**
`piano_voice` 在 `ld_for_me`（装载完成那一拍）把 6 个泛音包络**直接置到目标值**
（`env[j] <= {ld_env_flat[...], 16'd0}`），**没有斜坡**。
所以"从 note-on 到可闻"就是上面那个 10~20 µs，与包络无关 ✓
（实测也印证：L1 与 L2 两个口径的分位数**完全相同** —— 一出现就已经 ≥ −60 dBFS。）

### 3.2 独立的 `adsr.v` **不在钢琴通路上**（有 `top.v` 代码证据）
```
top.v:233  piano_engine u_piano ( ... .mix_out (mix_piano) ... );
top.v:252  .mix_out (mix_piano)      → 之后进 audio_fx → I2S
top.v:277  adsr u_adsr (ATK_SH(10), EN_DIV(512), ...)   // 只服务 tone_bank(32 路)
```
⇒ `adsr.v` 的 **10.5 ms** 起音（1024 步 × 10.24 µs，它的注释自己也写了 ≈10.5 ms）
**只影响 MODE=2 的 32 路测试音源**，不影响钢琴 ✓

### 3.3 ⚠️ 但这是一条**集成风险**，请守住
**不要让钢琴输出经过 `adsr.v`**：一旦经过，延迟立刻变成 ~10.5 ms（到满幅），
**同时违反拓展③(5 ms) 和基础要求②(10 ms)**。
若将来需要给钢琴做"整机 ADSR"，必须在 `piano_engine` 内部做（它已有逐泛音包络），
且**起音时间要单列进延迟预算**。

## 4. 系统级合成（我的部分 + 别人的部分，分开列清）

| 段 | 归属 | 延迟 | 证据 |
|---|---|---|---|
| 触摸/按键检测 | `fpga-tools` | 0.33 ms | 其报告 |
| 按键去抖（`DB_MAX=2^17`） | Lead `top.v` | **2.621 ms** | `top.v` 注释 |
| UART + MIDI 3 字节 @115200 | `pc-link` `rtl/io` | ≈0.26 ms | 3×10 bit / 115200 |
| **`piano_engine`** | **本模块** | **0.0103 ~ 0.0205 ms**（P50 0.0154） | **本报告实测** |
| I2S/PT8211 一帧 | `pt8211_tx` | ≤0.0102 ms | 32 bit @ BCK=6.25 MHz |
| `audio_fx` 干路 | `song-demo` | **待其确认**（混响/延迟按设计另有延迟，干路应 ≈1 采样） | — |

- **按键路径合计** ≈ 0.33 + 2.621 + 0.0205 + 0.0102 ≈ **2.98 ms** ✅ < 5 ms（余量 ~2 ms）
- **MIDI 路径合计** ≈ 0.33 + 0.26 + 0.0205 + 0.0102 ≈ **0.62 ms** ✅✅

**⇒ 结论：5 ms 预算里真正吃紧的是按键去抖 2.621 ms（Lead 的 `top.v`），不是钢琴引擎。**
若还想留更大裕度，把 `DB_MAX` 从 2^17 降到 2^15（0.655 ms）可再省 ~2 ms —— 但那是 Lead 的文件。

## 5. 诚实说明
1. 本报告的延迟**只覆盖 `piano_engine` 到 `mix_out`**；`audio_fx`、`pt8211_tx`、
   以及 `top.v` 里 `bus_*` 的选路延迟**不在我的写作用域内，未实测**（表中已标注归属）。
2. "可闻"用 −60 dBFS 阈值；若改用 −40 dBFS 或"到达峰值 50%"，**结论不变**
   （因为钢琴是瞬时起音，L1 与 L2 分位数相同）。
3. 抖动上界 20.5 µs 是在 `sample_tick` 周期 512 clk、`OUT_SHIFT=1`、8 声部配置下测的。
   改 `sample_tick` 频率（采样率）会**线性改变**这个上界。
4. P50/P95/P99 是在"note-on 相位均匀分布"假设下，对 512 个相位**全枚举**得到的**精确分布**，
   不是抽样估计 ⇒ 分位数本身没有统计误差。
