## 3. 烧录（**命令的确切用法**）

```powershell
# 三个模式都是同一条命令，只换 -Fs 指向的文件
powershell -NoProfile -ExecutionPolicy Bypass -File tools\gowin\program.ps1 -Mode sram `
    -Fs out\bitstream\MODE1_电脑控制.fs
```

### ⚠️ 三个必须知道的点
1. **脚本参数是 `-Mode`，没有 `-Op`**。
   `op 2` 是**脚本内部**传给 `programmer_cli` 的：`-Mode sram` → `op 2`（L176）、`-Mode flash` → `op 9`（L181）。
   **写 `-Op 2` 会直接报"找不到参数"。**
2. **别用操作码 4**（"SRAM Program **and Verify**"）。
   脚本源码注释实测记录：**本板（Tang Mega 138K + 板载 FT2232H）的【回读校验通路不可用】**，
   用 op 4 **必然报 `Error: Verify failed of at 0`**，**但位流其实已经正确写入**。
   ⇒ **这是假失败**，Sipeed 官方文档用的也正是**不带 Verify 的操作码 2**；耗时也从 ~106 s 降到 ~21 s。
3. **第一次上板一律用 `-Mode sram`**（易失、掉电即丢、**不动 Flash**），确认无误再考虑 `-Mode flash`。

| `-Mode` | 内部操作码 | 作用 |
|---|---|---|
| `scan` | — | 只扫描，确认缆线与器件被识别 |
| **`sram`**（默认） | **2** | **SRAM Program，易失** ⇒ 反复调试用这个 |
| `verify` | 2 + `--svfcreate` | **不需要板子**！解析位流并生成 JTAG 向量文件 |
| `flash` | **68** | **exFlash Erase,Program thru GAO-Bridge Arora V**（**会改写板上 Flash**，上电自动运行）|

## 4. ⚠️ 关于位流哈希与 `User Code`（**重要，别误判**）

### 4.1 **不要用 `.fs` 的 SHA256 判断"两个位流是不是同一版设计"**
实测：**同一份 RTL 连续构建两次，哈希就不同**（高云的时序驱动 P&R **是非确定性的**）。
**⇒ 判断修订要哈希【RTL 源码】，不是位流。** 详见 [../README.md](../README.md) 附录 B。

### 4.2 **`User Code` 也不是设计标识，而是【逐次构建的随机量】**
实测证据：
- `tools/gowin/program.ps1` 自己注释里记着**同模式的另外两个值**（测试模式 `0x0000A86D`、演奏模式 `0x00005093`）
- 后来构建的同类模式得到 `0x0000BB21` / `0x0000C7B0` ⇒ **同模式、不同次构建，值不同**
- `build.tcl` / `*.gprj` / `*.gprj.user` 里**都没有 `user_code` 设置**

**⇒ 它唯一可靠的用途**：烧录当场确认"我烧的就是我要烧的那个文件"（配合大小 / sha256）。
**⇒ 不能用它核对"重建结果是否等于历史产物"。**

### 4.3 ⚠️ **MODE=2 的原证据版位流已丢失**
`MODE2`（赛题必备交付物）**原来那份位流**（`User Code 0x0000BB21`）**没有归档**，
被后续构建覆盖了（工程里的 `impl/pnr/fpga_hank.fs` 每次构建都覆盖，而**没有自动归档脚本**）。
**⇒ 现在有的是【重建版】**（`68F7FFD22A9B1B18` / 18:37:18），
**两者不是同一份文件**（P&R 非确定性 + User Code 随机），**但 MODE=2 的 RTL 未变 ⇒ 功能等价**。

> ✅ **已批准、待实现的修法**：给 `build.tcl` 加**自动归档**（见 [../README.md](../README.md) §7）。
> **⇒ 在它实现之前，请务必【手动归档】**（见本文档 §2 第 ④ 步）。
