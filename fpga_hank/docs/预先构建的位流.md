# out/bitstream —— 预先构建好的两个位流

**由 Lead 在 2026-10-03 用当前 RTL 实测构建**，上板时**直接烧这两个文件即可，不必自己再构建**。

| 文件 | 模式 | 大小 | 用途 |
|---|---|---|---|
| `fpga_hank_TESTMODE0_演奏模式.fs` | `TEST_MODE = 0` | 34 840 489 B | ★ **插耳机听声音、按按键演奏** |
| `fpga_hank_TESTMODE1_测试模式.fs` | `TEST_MODE = 1` | 34 840 489 B | ★ **频谱取证：数 32 根谱峰**（赛题必备） |

烧录用：

```powershell
# 演奏模式
powershell -NoProfile -ExecutionPolicy Bypass -File tools\gowin\program.ps1 -Mode sram `
    -Fs out\bitstream\fpga_hank_TESTMODE0_演奏模式.fs

# 测试模式
powershell -NoProfile -ExecutionPolicy Bypass -File tools\gowin\program.ps1 -Mode sram `
    -Fs out\bitstream\fpga_hank_TESTMODE1_测试模式.fs
```

（不加 `-Fs` 时默认用 `eda_proj\...\fpga_hank.fs`，那是最近一次构建的产物。）

## 两个模式的构建结果（均实测）

| 项 | `TEST_MODE = 0`（演奏） | `TEST_MODE = 1`（测试） |
|---|---|---|
| 构建耗时 | 115.9 s | 85.9 s |
| Logic | **5986** / 138 240 | **5920** / 138 240 |
| Register | **1745** / 139 095 | **1699** / 139 095 |
| DSP | 58 / 298 | 58 / 298 |
| BSRAM | 1 / 340 | 1 / 340 |
| I/O Port | 12 / 297 | 12 / 297 |
| **时序违例** | **Setup 0 / Hold 0** | **Setup 0 / Hold 0** |
| **引脚 constrained** | **12 / 12** | **12 / 12** |

**差异说明**：演奏模式多出 **66 个 LUT + 46 个 FF** —— 那是三个按键的
**两级同步器 + 去抖计数器**（测试模式下按键不参与 gate，会被优化掉）。
其余资源完全相同，说明两种模式**共用同一条音频通路**。

> ⚠️ **为什么特意验证了演奏模式的综合**：此前所有构建都是 `TEST_MODE = 1`，
> 演奏模式只在**仿真**里例化过、**从未真正综合过**。
> 而它恰恰是"插上板子听声音"要烧的那个 —— 不验证就先上板，
> 万一综合阶段出问题（时序、资源、被优化掉），会白折腾。
> 现已确认：**两种模式都能综合、时序都零违例、引脚都全约束**。

## ⚠️ 关于位流哈希（重要，别误判）

**不要用 `.fs` 的 SHA256 判断"两个位流是不是同一版设计"。**
实测：**同一份 RTL 连续构建两次，哈希就不同**（高云的时序驱动 P&R 是非确定性的）：
```
构建 A  34840489 B  Logic 5986  FF 1745  DSP 58  违例 0/0  4EE27EFE…
构建 B  34840489 B  Logic 5986  FF 1745  DSP 58  违例 0/0  ?
```
判断修订要**哈希 RTL 源码**，不是位流。
详细说明见仓库根 `README.md` 的「一条重要方法论：位流的 SHA256【不能】当修订标识」。
